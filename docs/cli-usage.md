# CLI usage

## Build

```sh
git clone https://github.com/satty-br/huginn
cd huginn
go build
```

This produces a `huginn` (or `huginn.exe` on Windows) binary in the current
directory, built from the module at `github.com/satty-br/Huginn`
(Go ≥ 1.20; `go.mod` pins the toolchain version).

## Flags

| Flag | Default | Required | Meaning |
|---|---|---|---|
| `-file` | *(none)* | yes | Path to a gitleaks JSON report (`gitleaks detect --report-format json`). |
| `-project` | `./` | no | Root of the scanned project. Some validators read other files under this path for context (a self-hosted service's domain, a paired secret) — see [architecture.md](architecture.md#validation-patterns). |

Run `huginn -help` for the flag list generated by the standard library's
`flag` package.

## Behavior

```sh
./huginn -file ./results.json -project ./project
```

1. Prints the Huginn banner.
2. Exits with status `-1` and a red error line if `-file` was not given, or
   if the path it names does not exist. These two checks happen before
   `Runner` is ever called.
3. Calls `Runner(file, project)`. If it returns an error (the file couldn't
   be read as JSON, or `output.json` couldn't be written), the error is
   printed in red and the process exits with status `-1`.
4. For every secret Huginn could confirm against its real upstream service,
   prints a green `Secret '<value>' is valid!` line as it goes.
5. On success, writes `output.json` in the current working directory: the
   same array as the input report, with a `valid` field added to every
   entry (`true` only for secrets Huginn could confirm; `false` both for
   secrets it checked and found invalid/expired, *and* for any `RuleID` it
   has no validator for at all — see [validators.md](validators.md) for
   which is which).
6. Prints `Done!` in green.

Exit code is `0` on a full, successful run (even if every single secret
turned out invalid — that is a valid, successful run of the tool) and
non‑zero if the CLI usage was wrong or `Runner` itself failed.

## Docker

```sh
docker build -t huginn .
docker run --rm -v "$PWD:/data" huginn -file /data/results.json -project /data/project
```

The `Dockerfile` is a two-stage build: `golang:1.21.6` compiles a static
(`CGO_ENABLED=0`) binary, which is then copied into a minimal `alpine:3`
image that runs as a non-root `huginn` user with `huginn` itself as the
image's `ENTRYPOINT` — so every `docker run` argument after the image name
is passed straight through as CLI flags, exactly as shown above.
